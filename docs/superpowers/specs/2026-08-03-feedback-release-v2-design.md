# 第二版反馈能力与上架修复设计

## 目标

修复 AppGallery 审核指出的“设置开启振动反馈/音效后无反馈”，同时消除短音效播放状态竞态、补齐决策工具反馈覆盖，并以 `1.0.1` 作为第二个上架版本完成全量回归和自我审核。

## 已确认根因

1. 设置页的振动和音效开关只调用 `AppStore.updateSettings()` 保存布尔值，没有在由关闭切换为开启时触发预览。审核员严格执行“设置 → 反馈 → 开启”时，界面状态虽然更新，却没有可感知证据。
2. `SoundService` 给 `AVPlayer.fdSrc` 赋值后立即调用 `prepare()`。SDK 要求 `prepare()` 只能在播放器进入 `initialized` 状态后调用，而文件源赋值引起的状态变化是异步的，因此现有实现存在 `5400102` 状态错误和静默失败风险。
3. 指尖选择和随机数字只触发振动，没有接入音效；反馈开关的实际覆盖与用户对全局“音效”设置的预期不一致。
4. 应用元数据和设置页“关于”文字仍为 `1.0.0`，不能用于第二次上架。

## 修复范围

### 设置页即时预览

- 将振动与音效更新改为各自的异步处理方法。
- 先等待设置持久化成功，再在值为 `true` 时触发一次预览；从开启切换为关闭时不产生反馈。
- 振动预览使用短促、清晰但不过强的时长；音效预览使用现有 `tap.wav`。
- 保存失败时显示现有失败提示，保持原设置值，不播放预览。
- 自动保存历史和主题设置的现有行为不改变。

### 短音效服务

- 使用 HarmonyOS `SoundPool` 替代面向长媒体状态机的 `AVPlayer`。`SoundPool` 从 API 10 起可用，当前发布兼容范围满足要求，并原生支持 rawfile 短音效的加载和低延迟播放。
- Ability 创建窗口阶段初始化服务，加载 `sounds/*.wav` 并缓存 sound ID；播放时只按枚举查找并调用 `play()`。
- 初始化尚未完成时，首次播放等待同一个初始化 Promise，避免重复创建或丢失第一次预览。
- 后台阶段释放 SoundPool、卸载映射并关闭 raw FD；回到前台时重新初始化，确保后台释放后音效仍可恢复。
- 服务继续读取 `AppStore.settings.soundEnabled`，关闭音效时直接返回，不创建播放流。
- 失败只记录不含隐私和路径细节的警告，不阻断决定流程；返回值用于设备测试判断调用是否成功。

### 反馈覆盖

- 转盘、抽签、硬币和是或否保留现有触发时机。
- 指尖选择在最终选中时增加结果音效，与现有 80ms 振动同时触发。
- 随机数字成功生成结果时增加结果音效；输入校验失败时不产生成功反馈。
- 所有页面继续通过共享服务读取全局设置，不在页面复制权限、播放器或存储逻辑。

### 第二版元数据

- `AppScope/app.json5` 更新为 `versionCode: 1000001`、`versionName: "1.0.1"`、`buildVersion: "2"`。
- 设置页关于文字同步显示“做个决定 · 1.0.1”。
- 不修改包名、厂商、签名身份、应用图标或发布设备范围。
- 自我审核核对 README、构建 SDK 配置和实际产物，消除 API 版本陈述不一致；若签名材料约束导致无法统一，以实际构建证据记录，不伪造结论。

## 组件边界与数据流

1. 用户操作设置开关。
2. `SettingsPage` 等待 `AppStore.updateSettings()` 完成。
3. `AppStore` 只有在 Preferences 持久化成功后才替换内存设置。
4. 开启成功时，页面调用 `FeedbackService.impact()` 或 `SoundService.play(TAP)`。
5. 共享服务再次检查全局开关，调用系统振动或已加载的 SoundPool。
6. 任何系统能力失败都返回 `false` 并记录安全日志；设置仍按持久化结果保留，不回滚无关配置。

页面只负责“何时反馈”，服务负责“是否允许和如何调用系统能力”，存储层继续只负责持久化。

## 测试设计

### 自动回归

- 先增加失败测试，证明开启成功会请求一次对应预览、关闭或保存失败不会请求预览。
- 为短音效资源映射、初始化去重、关闭开关短路、后台释放与前台重建增加可重复测试；系统播放器边界通过最小接口注入隔离，测试行为而非平台实现细节。
- 增加六个工具反馈覆盖断言，防止后续页面遗漏音效或振动调用。
- 增加版本一致性检查，确保 AppScope 元数据与设置页显示相同。

### 构建和静态检查

- 执行 `scripts/check-standard.ps1`。
- 执行 `scripts/build-harmony.ps1`，同时构建主 HAP 和测试 HAP。
- 执行 `git diff --check`，检查资源引用、权限和不应出现的网络/媒体读取能力。
- 检查发布产物中的版本号、包名、签名状态和 WAV 资源均符合预期。

### 设备验证

- 在当前 HarmonyOS phone 模拟器安装新主 HAP 与测试 HAP，运行完整 Hypium 套件并要求 Failure 0、Error 0。
- 严格复现审核路径：先关闭再开启振动/音效，确认开关持久化以及预览调用结果；音效同时通过可听结果和系统日志复核。
- 六个工具各执行至少三次，验证开启时反馈、关闭时静默、动画期间防重复、切后台释放及回前台恢复。
- 模拟器不能证明物理马达振感。若当前没有真机，只把 API 成功、权限声明和调用日志记录为代码/模拟器证据，并将真机触感标为待发布前人工确认。

## 自我审核清单

- 根因修复覆盖审核原步骤，而非仅在其他决策页面产生反馈。
- 不改变随机算法、结果预计算、历史保存或模板数据结构。
- 不引入网络、麦克风、媒体读取或其他新权限。
- SoundPool、raw FD、回调和生命周期均有成对释放。
- 快速连续操作、初始化失败、后台切换和关闭开关没有资源竞争或误反馈。
- 版本号在配置、界面、变更记录和 QA 文档中一致。
- 不把签名口令、令牌、用户数据或本机敏感路径写入 QA 证据和发布说明。
- 保留工作区已有改动，不顺带回退或重构无关 UI。

## 发布完成条件

只有在静态检查、主/测试 HAP 构建、全量自动测试和可用设备回归均取得新鲜证据后，任务才能标记为 `done`。任何未具备设备条件的项目必须明确记录为 `blocked` 或待人工确认，不能用代码检查替代真实硬件结论。
